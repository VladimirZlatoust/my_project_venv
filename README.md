# Spam/Clickbait Classifier (Russian) — ML-проект с полным CI/CD пайплайном


## 1. Обзор проекта

Название: spam_clickbait_classifier_ru
Версия: 1.0 (Текущая рабочая модель — «Чемпион»)
Главная задача: Автоматически определять тип русскоязычного сообщения. Система должна отнести сообщение к одному из трех классов:

    Класс 0: Обычное/Легитимное сообщение (например, переписка друзей).
    Класс 1: Спам (реклама, мошенничество).
    Класс 2: Кликбейт (заголовки, заманивающие пользователя кликнуть ради рекламы).

Цель: Проект включает в себя систему автоматической проверки качества кода (CI/CD), чтобы гарантировать, что модель работает стабильно и код соответствует стандартам.

Ключевые метрики:

| Метрика |Что означает| Значение |
|---------|---|----------|
| F1-weighted |Средняя точность по всем трем классам с учетом их количества. Чем ближе к 1.0, тем лучше.  | **0.9455** |
| F1 (Clickbait/Класс 2) |Качество распознавания именно кликбейта (Класс 2).| **0.8823** |
| Recall (Normal/Класс 0) |Доля обычных сообщений, которые система правильно распознала как обычные (не приняла за спам). Важно, чтобы не было ложных тревог.| **0.9522** |
| Recall (Spam/Класс 1) |Доля спама, который система успешно поймала.| **0.9632** |
| Recall (Clickbait/Класс 2) |Доля кликбейта, который система успешно выявила.| **0.9001** |
| ROC-AUC (OvR, weighted) |Общая способность модели различать классы между собой. Значение близко к 1.0 говорит об отличной дискриминационной способности.| **0.9892** |
| Accuracy @ max P ≥ 0.60 |Если модель уверена в своем ответе более чем на 60%, то она права в 97.36% случаев. Это помогает фильтровать сомнительные ответы.| **97.36%** |


**Технологический стек:** 
- Язык: Python 3.11
- ML-библиотеки: scikit-learn (базовые алгоритмы), XGBoost/LightGBM/CatBoost (градиентный бустинг), Optuna (подбор параметров).
- Работа с данными: Pandas, NumPy.
- Управление проектом: MLflow (трекинг экспериментов), SAS Viya (корпоративная интеграция), BPMN 2.0 (стандарт описания бизнес-процессов).

## 3. Рефакторинг кода с использованием Ruff и Black (`model.ipynb`)

### Исходное состояние:
Изначально ноутбук model.ipynb выглядел как типичный исследовательский черновик: смешанные стили, жестко прописанные пути, отсутствие единого формата. 
Примены инструменты автоматического контроля качества кода:
- Black: Автоматический форматтер, переписывает  код так, чтобы он всегда выглядел одинаково красиво и единообразно во всей команде.
- Ruff: Быстрый  современный линтер (проверщик ошибок), находит неиспользуемые переменные, ошибки в импортах и нарушения стиля программирования.

### Примененный рефакторинг

| Аспект | До | После (принуждается CI) |
|--------|-----|------------------------|
| **Форматирование** | Разное количество пробелов, разные отступы | Единый стандарт (ширина строки 88 символов)`Black` (line-length=88, py311) |
| **Импорты** | Разбросанные, есть неиспользуемые | Отсортированы по алфавиту, лишние удалены`Ruff` (`isort` known-first-party=["model"], E/W/F/B/UP) |
| **Стиль кода** | Смесь стилей, возможные баги | Соответствие правилам PEP8 и современным практикам `Ruff` lint (E, W, F, I, B, UP) |
| **Гигиена ноутбука** | Сохранены выводы ячеек (графики, текст) | Выводы удалены перед коммитом (чистый diff)`nbstripout --verify` принудительно |

### Конфигурация инструментов
Находится в файле `pyproject.toml`, указывает, какие правила применять.

```toml
[tool.black]
line-length = 88
target-version = ['py311']
extend-exclude = '''
/(
    \.git
  | \.venv
  | venv
  | \.mypy_cache
  | \.pytest_cache
  | build
  | dist
)/
'''

[tool.ruff]
line-length = 88
target-version = "py311"
exclude = [".git", ".venv", "venv", "build", "dist", "__pycache__"]

[tool.ruff.lint]
select = ["E", "W", "F", "I", "B", "UP"]
ignore = ["E501"]  # Black отвечает за длину строки

[tool.ruff.lint.isort]
known-first-party = ["model"]
```

### Принуждение через CI (`.github/workflows/notebook-check.yml`)

```yaml
# Запускается при push/PR в main при изменениях model.ipynb, requirements*.txt, pyproject.toml
jobs:
  lint-and-test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with: { python-version: '3.11' }
      - name: Install deps
        run: |
          python -m pip install --upgrade pip
          pip install virtualenv
          virtualenv venv
          source venv/bin/activate
          pip install black ruff nbconvert nbstripout
          pip install -r requirements.txt
      - name: Check imports with Ruff
        run: ruff check --select I model.ipynb
      - name: Check formatting with Black
        run: black --check model.ipynb
      - name: Lint with Ruff
        run: ruff check model.ipynb
      - name: Verify notebook has no outputs
        run: nbstripout --verify model.ipynb
```

### Результаты рефакторинга:
- **Нулевые ошибки линтинга** при пуше
- **Единообразное форматирование**
- **Нет ячеек с выводами** в коммитах (чистые диффы)
- **Чистота импортов** (нет неиспользуемых, отсортированы)

## 4. CI/CD пайплайн и тесты

CI/CD (Continuous Integration / Continuous Deployment) — это процесс, когда GitHub автоматически проверяет код каждый раз, когда осуществляется git push. Если проверка не проходит, код не попадет в основную ветку (main).
Проверка запускается автоматически, если изменен один из следующих файлов и их отправили в ветку main:

    model.ipynb (сам ноутбук)
    requirements*.txt (список зависимостей)
    pyproject.toml (настройки линтеров)

### Триггеры пайплайна (`.github/workflows/notebook-check.yml`)|

### Этапы пайплайна (все должны пройти)

| Этап | Инструмент | Действие | Комментаррий и критерий прохождения |
|------|------------|---------|----------------------|
| **1. Checkout** | `actions/checkout@v5` | Скачиваем код с GitHub | Создаем чистое окружение для теста. Репозиторий клонирован |
| **2. Python Setup** | `setup-python@v6` |  Устанавливаем Python 3.11 |  Python 3.11 активен |
| **3. Установка зависимостей** | `pip` | Устанавливаем нужные библиотеки (scikit-learn, pandas и др.). `virtualenv venv && pip install black ruff nbconvert nbstripout -r requirements.txt` | Все зависимости установлены |
| **4. Проверка импортов** | `ruff check --select I` | Смотрим, правильно ли отсортированы и использованы импорты| Избегание ошибок "Module not found" или мусора в коде. Код возврата 0 |
| **5. Проверка форматирования** | `black --check model.ipynb` | Сверяем стиль написания кода со стандартами | Единообразие написания кода. Код возврата 0 |
| **6. Линтинг** | `ruff check model.ipynb` | Поиск потенциальных багов и нарушений стиля E/W/F/I/B/UP | Повышение надежности кода. Код возврата 0 |
| **7. Гигиена ноутбука** | `nbstripout --verify` | Проверяем, нет ли лишних выводов в .ipynb | Чтобы история изменений была чистой и легкой для понимания. Код возврата 0 |

## 6. Документация модели (Архитектура управления)

В проектах недостаточно просто построить модель. Нужно документировать её жизненный цикл. 
В настоящем проекте три ключевых документа:

### `model_card.md` — Model Card (Артефакт управления) — Паспорт модели
Главный документ для менеджеров и инженеров. Он отвечает на вопросы: «Что умеет модель? Насколько ей можно доверять?»
- Идентичность: Модель spam_clickbait_classifier_ru v1.0.
- Назначение: Обнаружение спама и кликбейта в реальном времени (SMS, Telegram, WhatsApp).
- Метрики качества: F1-score 0.9455. 
- SLA (Service Level Agreement — Соглашение об уровне сервиса):
- Модель должна поддерживать F1-score не ниже 0.92.
- Задержка ответа (latency) не более 200 мс.
- Если качество падает ниже этих значений, запускается процедура переобучения.
- Дрейф данных (PSI): Используется показатель PSI (Population Stability Index). Если PSI > 0.2, значит данные изменились слишком сильно, и старую модель пора обновлять.
- Human-in-the-loop (HITL): Если модель неуверенна (вероятность класса между 0.60 и 0.80), решение принимает человек-эксперт. Это повышает безопасность.

### `Model_BPMN.md` — BPMN 2.0 Операционный процесс — Схема рабочего процесса
BPMN (Business Process Model and Notation) — это международный стандарт для схем бизнес-процессов. 
Описано, как сообщение проходит через систему.
Суть потока:
- Получаем сообщение.
- Очищаем текст (удаляем эмодзи, опечатки).
- Классифицируем моделью.
- Шлюз G01: Если уверенность высокая (>60%) → Отправляем результат пользователю.
- Шлюз G02: Если уверенность средняя → Передаем эксперту для ручной проверки.
- Логирование результатов в базу данных.
 
Интеграция с SAS: Процесс связан с корпоративными сервисами SAS (Model Manager, Monitor).
**Формат:** OMG BPMN 2.0.2 + Mermaid диаграммы + исходники Mermaid (`bpmn_operation_v2.mmd`, `bpmn_operation_lanes.mmd`, `bpmn_operation_zoom.mmd`, `mc_flow.mmd`, `mc_sas_integration.mmd`)


### `Model_retrain_BPMN.md` — BPMN 2.0 Процесс переобучения — Схема обновления модели
Описывает процедуру, когда и как обучается новая версия модели, чтобы заменить старую.
Триггеры запуска переобучения:
- Превышен порог дрейфа данных (PSI > 0.2).
- Упала точность модели (ниже SLA).
- Ручной запрос специалиста.
- Плановое обновление по расписанию.

Этапы:
- Сбор новых размеченных данных.
- Обучение новой модели.
- Сравнение новой и старой мдели на тестовой выборке.
- Если новая модель лучше — деплой (поэтапное включение: сначала 10% трафика, потом 100%).
- Обновление документации (model_card.md).
